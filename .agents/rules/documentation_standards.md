# Documentation & Planning Standards

Rules for writing, structuring, and maintaining Markdown documentation in oXyFlow: analytical artifacts, implementation/refactoring plans, canonical manifesto specifications, and the user-facing wiki.

---

## 1. Documentation Taxonomy & Boundaries

All documentation belongs to one of four clear tiers:

| Tier | Location | Scope & Purpose | Precedence & Rules |
| :--- | :--- | :--- | :--- |
| **Analytical Artifacts** | Artifact dir / root | Discovery, root cause analysis, flow mapping, evidence gathering | Source of truth for planning; strictly factual and code-backed. |
| **Implementation Plans** | Artifact dir | Step-by-step phased execution plans, task registers, test strategies | Planning stage only; strictly NO code/test modifications during planning. |
| **Manifesto Specifications** | `docs/manifesto/` | Canonical system specifications (`ENGINEERING.md`, `CLI.md`, etc.) | Describes what the code does NOW; planned features explicitly marked. |
| **Public Wiki** | `docs/wiki/` | Multilingual user guide (`en`, `pl`, `de`, `es`, `fr`, `pt-br`) for GitHub Pages | User perspective; synchronized across all 6 locales; Docsify-compliant. |

---

## 2. Human-Engineered Writing & AI Humanizer Rules (Wiki & Manifesto)

Documentation must read as if written by a seasoned systems engineer, not generated by an automated language model. Formulaic AI tropes, robotic fluff, and hollow marketing language are strictly forbidden.

### 2.1. Forbidden AI Clichés & Buzzword Ban List
Never use generic AI filler words or inflated corporate buzzwords:
- ❌ **Forbidden words**: *delve, testament, tapestry, pivotal, beacon, landscape, moreover, furthermore, realm, plethora, seamless, effortlessly, game-changer, transformative, revolutionize, robust, bespoke, vital role, foster, illuminate*.
- ❌ **Forbidden meta-announcements**: *"In today's fast-paced world...", "It is worth noting that...", "It is important to remember that...", "As previously mentioned...", "In conclusion, ...", "To summarize, ..."*.
- ❌ **Forbidden conversational padding**: *"Let's dive into...", "Sure! Here is...", "Let's explore..."*.

### 2.2. Tone, Voice & Sentence Rhythm (Burstiness)
- **Direct & Action-Oriented**: Use active voice and imperative mood (*"Run `oxy sw task-1`"*, not *"Users may choose to execute the task switching mechanism"*).
- **Rhythmic Variation**: Vary sentence length naturally. Mix crisp, 5-word statements with detailed technical explanations. Avoid the monotone AI cadence where every sentence is exactly 18–22 words.
- **Zero Tautology**: Do not repeat the heading in the opening sentence. If the section is `## Task Archival`, do not start with *"Task archival is the process of archiving tasks."* Start with what happens and how to do it.

### 2.3. Concrete Over Abstract
- Never praise the software or proclaim its excellence (*"oXyFlow offers an unparalleled tracking experience"*). State concrete operational facts: execution time, memory footprint, offline SQLite persistence, keyboard shortcuts.
- Provide real, copy-pasteable CLI commands, file paths, or UI steps instead of generalized advice.

### 2.4. Authentic Idiomatic Localization (The 6 Wiki Locales)
When translating or authoring in `pl`, `de`, `es`, `fr`, or `pt-br`:
- **No Translationese or Calques**: Avoid literal word-for-word translations from English that sound robotic in the target language (e.g. Polish: avoid unnatural participle chains like *"będąc zoptymalizowanym pod kątem..."* or literal translations of *"under the hood"* as *"pod maską"* where *"architektura wewnętrzna"* is meant).
- **Natural Engineering Phrasing**: Use terminology that practicing developers and sysadmins in that linguistic region actually use.

## 3. Discovery & Analytical Artifacts

1. **Evidence-Based Ground Truth**:
   - Every claim, file path, symbol, or flow must be directly confirmed in code before writing.
   - Never assume files or modules exist without inspecting them.
   - Point out exact line numbers and code snippets as proof of defects or architectural smells.
2. **Pragmatic Assessment**:
   - Do not treat every aesthetic inconsistency as an architectural violation.
   - Filter findings through KISS, YAGNI, and pragmatic SOLID.
3. **No Code Edits**: Analytical artifacts gather facts. Do not write or modify production code, tests, or configurations during Discovery.

## 4. Implementation & Refactoring Plans

### 4.1. Preparation Protocol (/grill-me)
Before drafting an implementation or refactoring plan:
1. **Verify Evidence**: Check that baseline discovery/analysis exists and is sufficiently detailed.
2. **Verify Standards Compliance**: Ensure goals do not contradict `AGENTS.md` or `.agents/rules/*`.
3. **Detect Ambiguities & Trade-offs**: Identify open architectural questions, risky assumptions, or missing requirements.
4. **Interview the User (Only When Necessary)**: Ask clarifying questions only if a missing answer blocks a viable plan; otherwise, make explicit, code-backed assumptions.
5. **No Blind Adoption**: Do not mechanically accept all recommendations from analysis. Every change must solve a real problem and respect architecture boundaries.

### 4.2. Mandatory 10-Section Plan Structure
Every implementation or refactoring plan must include:
1. **Goal & Scope**: What the plan improves and what is explicitly OUT of scope.
2. **Baseline Findings Summary**: Direct references to confirmed issues from analysis (no duplicate walls of text).
3. **Target State**: Concrete architectural state and module responsibilities after execution.
4. **Architectural Decisions**: Choices, constraints, trade-offs, and explicit assumptions.
5. **Implementation Phases**: Logical vertical slices with dependencies, subphases, and reviewer gates.
6. **Task Register**: Granular task cards with:
   - Unique ID (e.g., `REF-001`, `TASK-001`);
   - Problem & concrete evidence (files, lines);
   - Expected target state;
   - Scope of touched files and symbols;
   - Proposed technical solution;
   - Dependencies on other tasks;
   - Risks & impact on existing consumers;
   - Required automated tests (unit, integration, arch, E2E);
   - Measurable acceptance criteria.
7. **Testing Strategy**: Tiers of tests verifying behavior and architectural invariants (AAA/BDT, test builders).
8. **Risks & Mitigation**: Potential regressions, backward compatibility checks, rollback plans.
9. **Decision Points**: Blockers requiring user input before implementation can begin.
10. **Definition of Done / Completion Criteria**: Quantifiable criteria proving the plan has achieved its goal.

### 4.3. Invariants During Planning
- **Planning stage only**: NEVER modify code, tests, configs, or project documentation during planning.
- **No speculative names**: Do not invent hypothetical filenames or abstractions not yet validated.
- **Frozen reference**: Once approved by the user, the plan artifact is a frozen contract. Do not edit or tick/untick checkboxes during phase execution.

## 5. Manifesto Specifications (`docs/manifesto/`)

1. **Current Reality, Not Aspirations**:
   - Manifesto documents (`ENGINEERING.md`, `MASTERMAP.md`, `CLI.md`, `USERINTERFACE.md`, `USEREXPERIENCE.md`, `USER_GUIDE.md`, `INSTALLATION.md`) describe the system as it runs today.
   - Future or unmerged features must be explicitly marked as `[PLANNED]` or `[PROPOSED]`.
2. **Synchronous Updates**:
   - Whenever a change touches contracts, exit codes, architecture layers, CLI flags, or roadmap status, update the corresponding manifesto document in the **same commit**.
3. **Hierarchy of Truth**:
   - In case of discrepancy: `AGENTS.md` → `.agents/rules/*` → `docs/manifesto/*` → other docs. Never resolve contradictions silently; report them to the user.

---

## 6. Public Multilingual Wiki (`docs/wiki/`)

1. **Docsify Architecture**:
   - Served on GitHub Pages via Docsify. Root contains `.nojekyll`, `index.html`, `404.html`, `_navbar.md`.
2. **Rule of 6 Locales**:
   - Public documentation exists in 6 locales: English (`en`), Polish (`pl`), German (`de`), Spanish (`es`), French (`fr`), Portuguese-Brazil (`pt-br`).
   - Adding a new guide or modifying user workflows must be reflected across all 6 language directories or flagged to the user.
3. **Navigation & Links**:
   - Every locale has its own `_sidebar.md` and localized articles (`getting-started.md`, `timer.md`, `cli.md`, `interface.md`, `automation.md`, `faq.md`, `developer-build.md`).
   - Links inside articles must use relative markdown paths appropriate for Docsify routing without breaking multi-language switching.

---

## 7. Pre-Submission Quality Checklist for Documentation

Before submitting any documentation artifact or file change:
- [ ] Language passes the AI Humanizer audit: no banned words (*delve, tapestry, seamless, pivotal*), no artificial intros/conclusions, natural sentence burstiness.
- [ ] Every assertion is backed by verified code (no fictitious files or unverified claims).
- [ ] Analysis documents do not contain premature code modifications.
- [ ] Plans follow the 10-section structure with granular task IDs and acceptance criteria.
- [ ] No architecture tests were proposed to be deleted or weakened.
- [ ] Hierarchy conflicts are reported, not silently resolved.
- [ ] Manifesto changes reflect current reality, with planned features clearly marked.
- [ ] Wiki updates maintain Docsify navigation and respect all 6 locales without translationese.
