# Multi-Agent Development Workflow Standards

How AI orchestrators and specialist subagents collaborate, delegate tasks, manage semantic git branches, enforce single-commit pull requests, and ensure quality gates in oXyFlow.

## 0. Rules Are Requirements

Passing tests and a clean compiler are a prerequisite, not proof of compliance. Every delegated subagent and orchestrator must strictly enforce `AGENTS.md` and all rules in `.agents/rules/`. Code that compiles but violates these rules is a defect and must be rejected during cross-agent review.

## 1. When This Workflow Applies

This workflow applies whenever task execution involves delegation across multiple subagents or when the user explicitly requests multi-agent collaboration:

- **Multi-Agent Mode Triggers**:
  - User prompts specifying delegation: *"delegate to agents"*, *"split among agents"*, *"multi-agent execution"*, *"separate PR per agent"*, *"run subagents"*.
  - Implementation plans that define distinct, modular slices intended for autonomous execution across isolated branches.
- **Single-Agent Mode Fallback**:
  - When the user gives direct commands without delegation intent (*"implement this"*, *"fix issue X"*, *"proceed with phase 1"*), the process strictly follows [`.agents/rules/development_workflow_standards.md`](development_workflow_standards.md).

```text
Discovery & Analytical Artifact (Source of Truth)
   ↓
Implementation Plan (Modular Slices & Semantic Branch Mapping)
   ↓
[For Each Slice / Phase Sequentially]:
   1. Orchestrator prepares Task Brief & creates/targets semantic git branch
   2. Worker Subagents executes autonomously in isolated branch/workspace
   3. Worker Subagents conducts Unified Verification & creates exactly ONE commit
   4. Worker Subagents reports completion or escalates questions to Orchestrator
   5. Orchestrator reviews PR / diff (Cross-Agent Review)
   6. Phase Gate: Orchestrator presents PR summary to User and STOPS
   7. Upon User Approval: PR is merged, next slice branches from updated main
```

## 2. Agent Roles and Responsibilities

### 2.1. Lead Agent (Orchestrator)
- **User Interface**: Holds exclusive direct communication with the user in the main thread.
- **Architectural Custodian**: Owns the high-level implementation plan, guarantees layer boundaries, and verifies adherence to `AGENTS.md`.
- **Delegation Manager**: Dispatches worker subagents with concrete, self-contained Task Briefs.
- **Escalation Gateway**: When a subagent encounters an ambiguity, missing requirement, or blocking defect, the Orchestrator translates the issue into a concise, multiple-choice question for the user. Never guess unstated user requirements.
- **Review & Merge Coordinator**: Performs cross-agent code audits on subagent PRs and coordinates sequential merging after user sign-off.

### 2.2. Worker Subagents (Specialists / Workers)
- **Isolated Execution**: Works exclusively on its designated git branch and assigned workspace.
- **Strict Boundary Adherence**: Modifies only files explicitly allowed in the Task Brief. Never touches unrelated files or architecture layers.
- **Zero Speculation (Stop & Ask Protocol)**: If a requirement is unclear, ambiguous, or contradicts existing code, the subagent **must stop immediately** and report the question back to the Orchestrator. Speculative implementation is forbidden.
- **Self-Verification**: Runs the Unified Verification Gate (`bun run test`, `bun run check`) before declaring completion.
- **Single-Commit Preparation**: Stages changes and packages the entire slice into **exactly one commit** with a structured technical and business message.

## 3. Semantic Git Branching & PR Architecture

### 3.1. Prohibition of Throwaway Sequential Identifiers
Branches and pull requests must carry durable technical and business meaning. Arbitrary sequential markers (e.g. `phase-1`, `phase-2`, `step-3`, `subphase-1.1`) are **strictly prohibited** in branch names.
- ❌ **Forbidden**: `feat/ds-phase-1-cleanup`, `fix/phase-2-fixes`, `refactor/phase-3`
- ✅ **Required**:
  - `feat/ui-primitives-standardization`
  - `fix/theme-contrast-db-explorer-and-cli`
  - `refactor/shared-patterns-and-accessible-drawer`
  - `refactor/project-form-fields-and-layout-primitives`

### 3.2. Single-Commit PR Contract
Every pull request generated by a subagents must culminate in **exactly one commit**:
1. **Title**: Follows Conventional Commits with a clear scope and imperative mood (e.g. `feat(design-system): standardize UI primitives and clean up component hierarchy`).
2. **Body**: Contains 3–6 concise, bulleted explanations covering both **technical improvements** (e.g. AST rule compliance, token usage, a11y) and **business value** (e.g. theme readability, developer ergonomics, elimination of code duplication).
3. **No Intermediate Commits**: Fixes resulting from pre-review checks must be squashed or committed cleanly so the PR history remains a single logical atomic commit.

### 3.3. Sequential Merge Strategy
- PRs must be merged sequentially into `main`.
- Parallel merging of interdependent feature branches is forbidden to prevent merge conflicts and database/lock contention.
- Subsequent worker subagents must branch from the newly updated `main` (or explicitly rebased tip) after the preceding PR is approved and merged.

## 4. Delegation Brief Specification

When delegating a task to a subagents, the Orchestrator must provide an explicit **Task Brief** containing:

1. **Working Branch**: Exact name of the semantic branch (e.g. `feat/ui-primitives-standardization`).
2. **Goal & Business Context**: What problem is being solved and why.
3. **Permitted File Scope**: Explicit list of files and directories the subagent is authorized to create or modify.
4. **Architectural Invariants**:
   - Zero raw HTML form/table tags outside `src/components/ui/` (`no-raw-html-primitives`).
   - Zero theme branching or hardcoded color classes (`no-inline-theme-ternaries`).
   - All user-facing strings localized across all 6 locales via `translate(...)`.
   - Max nested `if` statements <= 2 (Rule of 3 Ifs).
   - Target file size <= 300 LOC (proactive decomposition).
5. **Exact Verification Commands**: Specific test suites and linters required for green status.
6. **Required Single-Commit Format**: Exact template for the final commit message.

## 5. Question Escalation & User Communication Protocol

```text
Worker Subagents encounters ambiguity / blocker
   ↓
Worker Subagent STOPS and reports to Orchestrator (with file, line, and options)
   ↓
Orchestrator evaluates issue against AGENTS.md & rules
   ↓
[If unstated requirement]: Orchestrator asks User in Main Thread (Multiple-Choice)
   ↓
User answers in Main Thread
   ↓
Orchestrator conveys decision to Worker Subagent
   ↓
Worker Subagent resumes execution
```

Worker subagents must never invent requirements, create speculative fallbacks, or bypass missing requirements.

---

## 6. Review Gates and Sign-Off

1. **Subagent Pre-Review Audit**: Worker subagent audits its own branch against `frontend_engineering_standards.md` / `backend_rust_engineering_standards.md`.
2. **Orchestrator Cross-Review**: Orchestrator inspects the diff (`git diff origin/main...HEAD`), validates architecture boundaries, and verifies that test suites pass.
3. **Phase Gate (User Review)**:
   - Orchestrator links the PR (`link_pull_request`).
   - Orchestrator displays the single-commit message, technical summary, and verification evidence.
   - Orchestrator **STOPS completely** and awaits user approval.
4. **Merge & Progression**: Only upon explicit user sign-off does the PR merge to `main`, allowing the next task to commence.
