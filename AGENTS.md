## Commands

Bun is the only JavaScript toolchain. Never use `npm`, `npx`, `yarn` or `pnpm`, and never commit `package-lock.json`.

| Purpose | Command |
| --- | --- |
| Install | `bun install` |
| Browser runtime | `bun run dev` |
| Desktop runtime | `bun run tauri:dev` |
| All Vitest tests (unit, integration, architecture) | `bun run test` |
| Single test file | `bun x vitest run tests/unit/path/to/file.test.ts` |
| Typecheck / lint | `bun run typecheck`, `bun run lint` |
| Rust tests / clippy / fmt | `bun run test:rust`, `bun run lint:rust`, `bun run fmt:rust:check` |
| Rust architecture tests | `bun run test:arch:rust` |
| E2E (Playwright) | `bun run test:e2e` |
| Regenerate TS bindings | `cargo test --manifest-path src-tauri/Cargo.toml --test export_bindings_when_testing` |
| Graphify build / update / diagnose | `bun run graphify:build`, `bun run graphify:update`, `bun run graphify:diagnose` |
| Graphify report / visualization | `bun run graphify:report`, `bun run graphify:viz` |

`bun run check` and `bun run test:quality` chain steps with `;`, so their exit code reflects only the last step. Read the full output, or run the steps individually, before declaring them green. CI runs each step separately.

## Architecture in One Page

```text
React UI  →  EngineRouter / PersistenceRouter  →  Runtime implementation  →  Engine / Storage
                                                   Tauri: IPC → Rust (SQLite)
                                                   Browser: EnginePlugin / PersistencePlugin (LocalStorage)
```

- **Routers** (`IRouter<T>`) only select the active implementation and expose domain sub-interfaces (`timer`, `metrics`, `timeLogs`, `validation`). No logic, no transformation.
- **Engine** owns all business logic: timer lifecycle, elapsed calculations, statistics, validation. Rust is the reference implementation; the browser `EnginePlugin` must behave identically.
- **Persistence** stores and retrieves data (CRUD, serialization, transactions). It never validates, computes metrics or orchestrates workflows.
- **Runtime** (Tauri, Browser) owns environment integration and native APIs. Shared components never know which runtime they run in.
- **UI** is a function of four independent dimensions: runtime, `LayoutVariant` (`Full`, `Medium`, `Compact`), `TextAndIconSize` (`small`, `medium`, `large`) and theme. Layout builders compose structure only; scale and theme are CSS-only.

Before writing code, decide which layer owns the change (Engine, Persistence, Runtime, Layout, React or CSS) and check whether an implementation already exists.

## Non-Negotiable Rules

Rules marked *(enforced)* fail the build automatically; the test name points to the source of truth.

1. Business logic lives only in the Engine, once per runtime. *(enforced: `engine-boundary`, `persistence-boundary` arch tests)*
2. Shared components never detect the runtime. *(enforced: `runtime-isolation` arch test)*
3. No raw `<button>`, `<input>`, `<select>`, `<textarea>`, `<table>`, `<thead>`, `<tbody>`, `<tr>`, `<th>`, `<td>`, `<label>`, `<p>`, `<form>`, `<aside>` outside `src/components/ui/`. *(enforced: `no-raw-html-primitives` arch test + ESLint)*
4. No theme branching in components (`theme === 'dark' ? …`). Use semantic tokens. *(enforced: `no-inline-theme-ternaries` arch test)*
5. No custom `setInterval` tickers for elapsed time; use `useLiveTaskElapsed` / `useLiveProjectElapsed`. *(enforced: `timer-live-calculation` arch test)*
6. No circular dependencies. *(enforced: `circular-dependencies` arch test, Rust `cyclic_dependencies_test`)*
7. All user-facing text goes through `translate(...)` / `useTranslation`, without `|| 'fallback'`. Keys belong to domains defined by `I18N_DOMAINS` in `src/common/i18n/keys.ts`; new keys go into their domain file `src/common/i18n/keys/<domain>.ts` and into all 10 locales (`en`, `pl`, `de`, `es`, `fr`, `pt-br`, `uk`, `ja`, `nl`, `it`) in `src/common/i18n/dictionaries/<domain>.json`.
8. No hardcoded colors or computed spacing in components; use design tokens.
9. TypeScript: no `any`, no `@ts-ignore` / `@ts-expect-error` to silence errors, no duplicated types (reuse `src/bindings/`).
10. Rust: no `String`, `Box<dyn Error>`, `()` or `anyhow` error types; use `thiserror` domain enums. *(enforced: `error_handling_test.rs`)*
11. Code, comments, test names and test IDs are in English.
12. Maximum nested `if` depth is 2. 3 or more nested `if` statements are forbidden across both TypeScript and Rust (Rule of 3 Ifs: depth >= 3 triggers failure). *(enforced: `max-nested-ifs` arch tests, Rust `max_nested_ifs_test`)*

## How to Work

### Default flow (every task)

```text
Understand → Choose layer → Contracts → Implementation → Tests → Documentation
```

- Ask the user when requirements are ambiguous; do not guess unstated requirements and do not invent architecture.
- Prefer the simplest solution. Introduce an abstraction only when it solves a problem that exists today.

### Graph-First Architecture Discovery & PR Sizing

When `graphify-out/` or the Graphify MCP server is available, assistants MUST apply the **Graph-First Architecture Discovery** pattern before reading large directories, planning decompositions, or editing code. Query the codebase knowledge graph via the `graphify` MCP server:

- `query_graph`: Ask questions about codebase topology, community clusters, and structural concepts.
- `shortest_path`: Trace exact dependency chains and call flows between modules across layers (e.g. UI → Router → Engine/Persistence).
- `get_community`: Inspect semantic module clusters to cut PRs along natural boundaries rather than arbitrary file splits.
- `get_neighbors`: Inspect immediate upstream and downstream dependencies before modifying interfaces or functions.
- `god_nodes`: Identify critical central hubs (e.g. `react`, `CliError`, `Persistence`) to prevent tight coupling or cyclic dependencies.
- `get_pr_impact` & `triage_prs`: Evaluate blast radius and cross-boundary ripple effects before opening or reviewing PRs.

When to use:
- **PR decomposition & sizing**: breaking large changes into bite-sized (100–300 LOC) PR chains along natural community boundaries.
- **Layer relationship auditing**: verifying that changes adhere to Clean Architecture without crossing unauthorized layer boundaries.
- **Impact analysis**: tracing callers and consumers before altering public signatures, domain types, or commands.
- **Pre-change dependency inspection**: evaluating ripple effects before adding dependencies or refactoring.

### Multi-phase tasks

Large features and roadmap phases follow the phase-gate process in [`development_workflow_standards.md`](.agents/rules/development_workflow_standards.md): implementation plan first, autonomous work within an approved phase, then stop and request review before the next phase.

### Refactoring scope

- Small cleanups inside code you are already changing are expected: rename unclear identifiers, remove dead code, replace a magic string, fix a rule violation on the touched lines.
- Proactive decomposition: Follow `.agents/rules/code_quality_standards.md` for LOC thresholds and exceptions. Treat LOC as a warning and review signal, not as an instruction to split files mechanically. Decompose when responsibilities, cohesion or maintainability justify it.
- Unrelated structural refactors across distant subsystems or contracts are proposed and done as a separate task or commit after approval.
- Never mix a feature, an unrelated refactor and an architecture change in one commit.

## Documentation Updates

Update documentation in the same change when you:

| Change | Update |
| --- | --- |
| Architecture, layers, contracts | `docs/manifesto/ENGINEERING.md`, and `AGENTS.md` if a rule changes |
| Naming and product identity | `docs/manifesto/NAMING.md`, `metadata.json` |
| Roadmap phase completed or started | `docs/manifesto/MASTERMAP.md` (Strategic roadmap/plan only; NEVER use as a changelog) |
| Feature, bug fix, or version delivered | `CHANGELOG.md` (Keep a Changelog format with version suffixes: `Added in X.Y.Z`, `Changed in X.Y.Z`, `Fixed in X.Y.Z`, `Removed in X.Y.Z`) |
| CLI command, flag, error code or exit code | `docs/manifesto/CLI.md` |
| Setup, scripts, features list | `README.md` |
| UI dimensions, tokens, design system | `docs/manifesto/USERINTERFACE.md` |

Documentation describes what the code does now. Mark planned behavior explicitly as planned.

## Definition of Done

- The change lives in the correct layer, and runtime / layout / scale independence is preserved.
- `bun run test`, `bun run typecheck` and `bun run lint` pass.
- If `src-tauri/` changed: `bun run test:rust`, `bun run lint:rust` and `bun run fmt:rust:check` pass.
- New behavior has tests in the correct tier (see `testing_standards.md`).
- Documentation is updated according to the table above.
- The final report states honestly what was verified, what was skipped and what failed.
